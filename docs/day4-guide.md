# День 4 — frontend и Docker: пошаговое руководство

Проект построен поверх Дня 3 (в архиве уже исправленный backend). Ниже: что добавлено, зачем, как запустить и как сдать.

## Шаг 0. Как положить файлы в репозиторий

1. Склонируйте репозиторий (если ещё нет): `git clone https://github.com/Tether4612/access_event.git`
2. Распакуйте архив `accessevent.zip` и **скопируйте содержимое папки `accessevent/` в корень репозитория с заменой файлов**.
3. Создайте файл `.env` (он не хранится в git) из `.env.example`: впишите свой пароль PostgreSQL.
4. Проверьте `git status`: должны появиться `templates/`, `static/`, `Dockerfile`, `docker-compose.yml`, `.dockerignore`, два новых workflow. Файла `.env` в списке быть не должно.

## Шаг 1. base.html — общий каркас (Задание 1)
Файл `templates/base.html` один раз описывает шапку, меню, подвал и подключает CSS/JS. Остальные страницы пишут `{% extends "base.html" %}` и заполняют только `{% block content %}`.
- `aria-label`, `role="main"`, `role="contentinfo"` — подсказки для экранных читалок.
- `<div aria-live="polite" id="notifications">` — сюда JS выводит визуальные уведомления.
- `url_for('index_page')` строит ссылку по **имени функции-маршрута** в app.py. Если такой функции нет, будет `BuildError`, поэтому Шаг 5 обязателен.
- Меню умеет два состояния: вошёл (Профиль, Выход) и не вошёл (Вход, Регистрация).

## Шаг 2. Пять страниц (Задание 2)
`index.html`, `events.html` (цикл `{% for %}...{% else %}` — `else` срабатывает при пустом списке), `login.html`, `register.html`, `profile.html`.
Отличия от методички (намеренные):
- в формах стоит `novalidate`: без него браузер сам останавливает пустую форму своим пузырьком и наше визуальное уведомление не появляется;
- у `<textarea>` убраны пробелы внутри тегов, иначе в базу попадали бы пробелы;
- у мероприятий убрана строка «Статус»: у события нет поля `status` (статус есть только у регистрации);
- дата выводится как `01.11.2026 12:00`; в профиле показано название мероприятия, а не его номер;
- эмодзи подписаны (`aria-label`) или скрыты от читалок (`aria-hidden`).

## Шаг 3. style.css (Задание 3)
Сетка `grid`, цветные бейджи (смысл всегда дублируется текстом, не только цветом), два медиа-запроса: `max-width: 768px` (2 колонки) и `480px` (1 колонка). Добавлены видимый фокус для клавиатуры и отключение анимации при `prefers-reduced-motion`.

## Шаг 4. main.js (Задание 4)
`showNotification(message, type)` создаёт блок в `#notifications` и удаляет его через 4 секунды. Звука нет — это требование доступности.

## Шаг 5. Маршруты страниц в app.py (Задание 5)
Добавлены `/`, `/events`, `/login`, `/register`, `/profile/<id>` (+ `/logout`). Отличия от методички:
- после входа id пользователя запоминается в `session` (подписанная cookie, нужен `SECRET_KEY`). В методичке любой мог открыть `/profile/1` и увидеть чужой email; теперь чужой профиль перенаправляет на вход;
- при регистрации роль `admin` через форму выбрать нельзя, проверяется и занятое имя;
- `context_processor` передаёт `current_user` во все шаблоны.

## Шаг 6. Dockerfile и .dockerignore (Задание 6)
- `FROM python:3.11-slim` — лёгкая база с Python;
- `COPY requirements.txt` + `pip install` **до** `COPY . .` — слой с пакетами кэшируется, пересборка занимает секунды;
- `CMD ["python", "app.py"]` — exec-форма, корректно реагирует на остановку;
- `.dockerignore` не пускает в образ `venv`, `.env` (секреты), `.git`, кэш.

## Шаг 7. docker-compose.yml (Задание 7)
- Два сервиса: `web` (наше приложение) и `db` (PostgreSQL 16);
- адрес базы внутри Docker: **`db:5432`**, не `localhost`;
- том `postgres_data` хранит данные вне контейнера;
- порт `5433:5432`, чтобы не конфликтовать с локальным PostgreSQL на 5432;
- вместо устаревшей строки `version:` не указана версия (Compose v2 её не требует и пишет предупреждение);
- вместо «подождите и сделайте restart»: у `db` есть `healthcheck`, а `web` стартует только когда база готова (`condition: service_healthy`).

Запуск:
```
docker compose up --build        # собрать и запустить
# браузер: http://localhost:5000
docker compose down              # остановить (данные остаются)
docker compose down -v           # остановить и удалить данные базы
```

## Шаг 8. GitHub Actions (Задание 8)
- `day4-check.yml` проверяет наличие файлов, размеры CSS/JS, `@media`, ARIA, Dockerfile, compose и собирает образ. В методичке проверки печатали FAIL, но не роняли job; теперь при FAIL job краснеет;
- `docker-publish.yml` собирает образ и публикует в GHCR. Имя образа переводится в нижний регистр (`ghcr.io/tether4612/access_event`), иначе GHCR отклоняет логин с заглавными буквами;
- в обоих файлах убраны строки с `PASS: ...` в обычном `run:`: двоеточие с пробелом ломает YAML.

## Шаг 9. Запуск локально (Задание 9)
```
venv\Scripts\activate
pip install -r requirements.txt
python app.py
```
Откройте http://127.0.0.1:5000 и пройдите чек-лист: главная, меню, адаптивность (сузьте окно), пустая форма входа (должно появиться красное уведомление и исчезнуть через 4 с), бейджи на карточках (сначала создайте мероприятие через Postman из Дня 3).

Если PostgreSQL недоступен (неверный пароль в `.env`), приложение само запустится на SQLite и напишет причину в терминал.

## Шаг 10. Коммит, push, проверка
```
git add .
git commit -m "День 4: frontend, Docker, GHCR"
git push origin main
```
Во вкладке **Actions** должны позеленеть **Day3 Backend Check**, **Day4 Frontend Check** и **Build and Publish Docker Image**. Образ появится в профиле → **Packages**; чтобы он был виден преподавателю: пакет → Package settings → Change visibility → Public.
